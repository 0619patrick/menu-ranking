## 一、产品是什么

一款**给餐饮集团运营老板用的销量数据自动化整理工具**。

把各家门店从 POS 系统导出的 Excel 文件上传进来，工具会按照标准菜单自动归类、汇总、排序，并生成可下载的「菜品销量对照表」Excel。

### 1.1 解决的核心问题

**月度汇总销量是餐饮老板的高频痛点**：
- 每家店每月导出 POS Excel（4 种不同格式）
- 人工对照菜单标准分类、整理销量排行
- 多店横向对比需要手动拼贴
- 单店 1-2 小时、多店多月份起步半天

**本工具一键解决**：上传 → 自动归类 → 多店并排 → Excel 下载。**整套流程 < 5 分钟**。

### 2.2 核心功能列表

#### 🍱 数据处理
- 上传 4 种 POS 格式 Excel（已实装 3 种：餐飲王 + 美團 + Keeta）
- 美團数据自动按 (大类, 菜名, 规格) 聚合

#### 📋 智能归类
- 菜单标准分类自动匹配
- POS 错放分类强制纠正（FORCE_CAT 规则）
- 套餐分类整体归"堂食菜單外"
- 套餐内的单品饭/面优先归"主食系列"
- POS 原生分类（如阿城内地卤味三档）整段直接以 POS 为准

#### 🏷️ 特殊业务
- **茶位高亮**（黄色背景行首）
- **外卖按平台分组**（Keeta / Foodpanda / Take 等多种标识）
- **補差價单列**（如泰菜的"手寫單"，金额负数）
- **加料拆分显示**（如四季芬芳的米線加料：「點餐 13 / ¥78 + 套餐內含 49 次」）
- **🆕 新菜标注**（菜单 PDF 没列但 POS 有售）

#### ⚠️ 配置警告（预览页实时体检）
- 预览时若**同一个 POS 写法被两道菜同时引用**（会导致销量/金额重复计算），
  表格顶部会显示黄色警告条，列出冲突写法、被哪几道菜引用、影响份数
- 点击警告条里的链接可跳转菜单配置页检查修复
- 修复前请用「下載 Excel」核对金额是否异常偏大
- 配合 `scripts/check_menus.py` 命令行体检（改表后跑一次更保险）

#### 📊 多店对比
- 同 sheet 内多店左右并排（每店 5 列：分類/排序/品名/數量/金額）
- 分类按菜单声明顺序对齐（同分类占同一行段，便于横向比较）
- 类内菜品按金额降序

#### 📂 分组导出
- **按 (地区, 品牌, 月份) 分 Sheet**：如「香港天天3月」「内地天天3月」
- **按品牌分 Excel 文件**：天天 + 阿城一起上传 → 输出 ZIP 含 2 个 .xlsx
- **单品牌直接下载** .xlsx，不打 zip
- Sheet 顺序稳定：品牌按上传顺序，内地 → 香港，月份升序

#### 🌐 用户界面
- 顶部 5 个餐厅 Tab，切换显示对应快速选店按钮
- 每店卡片：店名、餐廳预设、地区、月份、文件
- 餐廳下拉提供 7 种预设组合（覆盖所有现有店）
- 门店按钮按地理区域折叠展示（🇭🇰 香港 / 华南 / 华东 / 华北 / 华中 / 西南）
- 文件支持拖放或点击选择
- 网页预览 + 可校对疑似异常项（▶ 展开 / ✕ 删除）

#### 🏪 门店管理（Web 后台）
- 独立管理页面 `/admin`，免代码维护门店信息
- 门店数据持久化存储于 SQLite（当前 50 家门店）
- 支持新增、编辑、删除门店
- 所属餐厅、POS 类型、地区均可配置
- 地区支持二级级联选择：先选「香港/内地」→ 内地可再细分「华南/华东/华北/华中/西南」
- 门店列表按**品牌→地区**两级分组展示，默认折叠
- POS 类型支持文本输入 + 下拉建议（可自定义输入新 POS 平台）
- 修改后刷新首页即生效，无需改代码、无需重启服务

#### 🤖 AI 辅助匹配
- 预览时「菜單外」项目可点击 🤖 按钮
- 基于 `difflib.SequenceMatcher` 本地模糊匹配，不上传外部 API
- 自动推荐 top 5 标准菜名及匹配度百分比
- 确认匹配后自动追加 POS 写法到 `menu.csv`，下次预览生效

#### 🔌 POS API 自动拉取（框架就绪）
- 首页折叠面板「🤖 AI 自動拉取數據」，支持选择日期范围和门店
- 基于 BaseFetcher 抽象类 + Cleaner 清洗层架构设计
- 当前为框架层已就绪状态，待 POS 厂商提供 API 后对接即可启用
- 配套接口规范文档：`docs/POS_API_接口规范.md`

## 三、典型使用流程

### 3.1 单店生成排行表

1. 浏览器打开 https://menu-ranking.onrender.com
2. 顶部选餐厅 Tab（如「天天」）
3. 点快速选店按钮（如「沙田（餐飲王）」）—— 自动填好店名 + 餐廳预设
4. 选月份（默认当月）
5. 点击「POS 數據文件」区域 → 选择 POS 导出的 xlsx
6. 点「生成預覽」—— 几秒后预览出现在下方
7. 看预览，对照觉得没问题
8. 点「下載 Excel」—— 直接下载 .xlsx

### 3.2 多店混合上传

1. 顶部点对应餐厅 Tab，点快选按钮加店 1
2. 切到另一品牌 Tab，再点快选 → 加店 2
3. 重复加到所有要处理的店
4. 各店各自选月份/地区
5. 点「生成預覽」→ 下方 Tab 切换看每店预览
6. 点「下載 Excel」：
   - 若多品牌 → 下载 ZIP（每品牌一个 .xlsx）
   - 若单品牌 → 直接单 .xlsx
7. ZIP 解压后每个 .xlsx 内含按 (地区+月份) 分的 sheet

### 3.3 手动加店（自定义）

1. 点「+ 再加一家店」—— 默认套当前 Tab 的餐厅预设
2. 「店舖名稱」手动输入（如「香港天天太古城」）
3. 「餐廳」下拉：若快选不对，直接改（7 种预设全在）
4. 地区/月份按需选
5. 上传文件、生成預覽

### 3.4 AI 自动拉取（框架预览）

当 POS 平台开放 API 后，可通过自动拉取替代手动上传：

1. 在首页「🤖 AI 自動拉取數據」面板选择开始/结束日期
2. 确保已添加对应的门店卡片（POS 类型需匹配）
3. 点击「拉取數據」—— 系统调用 POS API 获取原始数据
4. 自动清洗为标准 4 列格式 → 匹配菜单 → 生成预览
5. 后续操作与手动上传一致（校对、下载）

> 当前仅框架就绪，需 POS 厂商提供 API 并实现 Fetcher 子类后方可实际使用。

## 四、特色业务规则详解

### 4.1 多店行级对齐

举例：同时上传天天 沙田 + 太古城，会输出一个 sheet「香港天天3月」，左右两栏：

```
分類       │ 排序 │ 品名         │ 數量 │ 金額    ║ 分類       │ 排序 │ 品名         │ 數量 │ 金額
天天海南雞 │ 1   │ 海南雞(中份) │ 753  │ 49,294 ║ 天天海南雞 │ 1   │ 海南雞拼烧雞 │ 238  │ 69,069
            2   │ 海南雞拼烧雞 │ 319  │ 41,953 ║              2   │ 海南雞(中份) │ 330  │ 52,390
            3   │ 海南雞(大份) │ 89   │ 23,602 ║              3   │ 海南雞(大份) │ 108  │ 30,923
```

两边的"天天海南雞系列"分类**占同一行段**，方便老板对比两家店的销量。

### 4.2 加料「點餐 vs 套餐內含」

四季芬芳的"自選靚湯米線"套餐含一个加料。POS 里同一道加料有 2 行：
- 价 6 元 / 数量 13 = ¥78（顾客单点）
- 价 0 元 / 数量 49 = ¥0（套餐内含送的）

工具自动拆分显示：

```
韭菜 (+$6)  〔套餐內含 49次〕   數量: 13  金額: ¥78
```

收费金额和内含次数都看得到，方便老板看一道加料"卖了多少 + 送了多少"。

### 4.3 POS 原生分类（深圳阿城卤味）

深圳阿城的「12元精选卤味/特色卤味/麻辣卤味/手作系列」在菜单 PDF 上没列具体菜品，但 POS 里有十几个项目。

工具把这 4 个分类设为「POS 原生分类」：
- 不打 🆕 标签（这本来就是该分类的内容，不是"新菜"）
- 全部 POS 项目直接按金额排进段内

### 4.4 套餐路由

POS「单人套餐」「双人套餐」分类下挂着各种"鹅肉饭+卤肉饭"等套餐组合。

- 整段归到"堂食菜單外"（不污染正餐排行）
- 但里头如果有单品饭/面（如「冬陰功汤面」），仍自动归到"主食系列"

## 五、技术架构（简述）

详见 GitHub 仓库 README 和源码注释。这里只列关键结构：

```
┌───────────────────────────────────────────────┐
│  浏览器（首页 + /admin 管理后台 + 预览表）    │
└──────────────┬───────────┬────────────────────┘
               │ HTTP      │ REST API
               ▼           ▼
┌───────────────────────────────────────────────┐
│  Flask (create_app) - 路由 + API + 参数校验   │
└──────────────────┬────────────────────────────┘
                   │
       ┌───────────┼───────────┬──────────────┐
       ▼           ▼           ▼              ▼
  ┌────────┐  ┌────────┐  ┌──────────┐  ┌───────────┐
  │  POS   │  │ Menu   │  │Transform │  │ Store     │
  │Adapter │  │ Service│  │(核心引擎) │  │ Service   │
  └────────┘  └────────┘  └──────────┘  └─────┬─────┘
   餐飲王     菜单读取     路由+聚合         └── SQLite
   美團       缓存管理     多店并排
   Keeta                   Excel 生成
```

**4 层分离**：
1. **POS Adapter**：把任何 POS 格式归一成 4 列标准 DataFrame（项目名称/分类/数量/金额）
2. **Menu Service**：菜单定义 + CSV 加载 + 内存缓存
3. **Transformer 核心引擎**：不关心 POS 是谁、菜单是哪份，统一处理
4. **Store Service**：门店 CRUD，数据持久化于 SQLite

**好处**：
- 加新 POS = 写一个 Adapter（不动任何餐厅）
- 加新餐厅 = 写一份 menu config（不动任何 POS）
- 加新门店 = 浏览器操作 /admin 页面，不改代码
- 业务规则集中在 menu 文件，开发者一处即可掌握

## 八、已知限制

1. **冷启动延迟**：Render Free 闲置 15 分钟后首次访问要等 30-60 秒
2. **大批量上传可能 OOM**：6-8 家店是 Free Plan 极限，10+ 建议升 Starter
3. **数据不持久化**：每次重新上传文件，不存历史月份（门店配置已持久化，但销售数据不存）
4. **单用户**：无登录、无权限隔离（适合小团队内部使用）
5. **POS 导出仍需手动**：当前仅实现适配器处理已导出的文件，未对接 POS 实时 API
6. **菜单更新需手动维护**：新菜上市或改名需修改 `app/data/menus/<brand>/menu.csv`
7. **零售周边 POS 项**：如「外賣盒」「打包盒」等已自动丢弃，但若 POS 新增其他周边项目需在 `drop_names` 中维护
8. **AI 匹配基于本地模糊算法**：`difflib.SequenceMatcher` 仅依赖字符串相似度，不识别语义别名（如「冻柠茶」≠「冻柠檬茶」），仍需人工确认
9. **POS 写法重复引用会双算**：同一 POS 写法被两道菜引用时销量/金额会重复计算（预览页会黄色警告提示）。历史上已在 4 家菜单中修复此类问题（2026-08），新增菜单时请保持 POS 写法唯一归属

## 九、运维 / 维护指南

### 9.1 加新店（Web 后台操作，推荐）

浏览器访问 `/admin` 页面，点「新增門店」填写：

| 字段 | 说明 | 示例 |
|---|---|---|
| 門店名稱 | 唯一标识，全称 | `香港天天銅鑼灣` |
| 顯示標籤 | 首页按钮显示的短名 | `銅鑼灣`（留空则用门店名称） |
| 所屬餐廳 | 下拉选择所属品牌 | `天天` / `阿城` / `四季芬芳` / `鮨政` / `泰菜` |
| POS 類型 | 文本输入 + 下拉建议，可自定义 | `canyinwang` / `meituan` / `keeta` / `pos365` / 自填 |
| 地區（一级） | `香港` / `内地` / `其他` | `香港` |
| 地區（二级） | 内地时可选 `华南` / `华东` / `华北` / `华中` / `西南` | 留空则归为「内地」 |

保存后，返回首页即可看到新店按钮——**无需改代码、无需重启服务**。

> 子品牌门店（如内地天天、深圳阿城）会自动归到所属主品牌 Tab 下显示。

### 9.2 加新菜（菜单更新）

编辑对应餐厅的 `app/data/menus/<brand>/menu.csv`，在末尾追加行：

```csv
分类,标准菜名,价格,单位,POS写法
前菜/小食,新菜名,49,份,POS写法1|POS写法2
```

- **分类**：必须使用该餐厅已有的分类名（参考 `config.csv` 中的 `section_order`）
- **POS 写法**：多个写法用 `|` 分隔，用于模糊匹配时识别 POS 菜名

编辑后刷新页面即可生效（系统有内存缓存，修改 menu.csv 后首次加载自动更新）。

### 9.3 加新餐厅（开发者操作）

1. 在 `app/data/menus/` 下新建文件夹 `<new_brand>/`
2. 创建 `menu.csv`（菜品列表）和 `config.csv`（分类顺序 + 路由规则）
3. 参考已有餐厅配置（如 `tiantian/` 或 `acheng/`）
4. 重启服务，系统会自动扫描发现新餐厅（无需在任何代码中注册）
5. 门店管理页面 `/admin` 新增门店时，所屬餐廳下拉框会自动包含新品牌

### 9.4 加新 POS 系统（开发者操作）

1. 在 `app/adapters/` 下新建 `<name>.py`，继承 `PosAdapter`，实现 `load(file_obj)` → 返回标准 4 列 DataFrame
2. 在 `app/adapters/__init__.py` 的 `ADAPTERS` 字典注册：
   ```python
   'new_pos': NewPosAdapter,
   ```
3. 门店管理页面新建/编辑门店时，POS 類型输入 `new_pos` 即可使用
4. 如需首页上传时下拉可选该 POS，需在 `index.html` 的 `RESTAURANT_PRESETS` 中补充组合

### 9.5 AI 辅助匹配

首页预览时，出现在「菜單外」区域的项目，点击 **🤖匹配** 按钮：

1. 弹出 AI 建议列表，显示最相似的 5 道菜单标准菜名及匹配度（百分比）
2. 点击某建议 → 自动将当前 POS 菜名追加到 `menu.csv` 对应菜品的 POS 写法列
3. 确认后下次预覽该行自动匹配到菜单内

> 匹配算法基于 `difflib.SequenceMatcher` 本地模糊匹配，不上传数据到外部 API。

### 9.6 数据库维护

门店数据存储在 `app/data/stores.db`（SQLite 文件）。

- **备份**：直接复制 `stores.db` 文件即可
- **重置**：删除该文件后重启服务会自动重建并导入种子数据（14 家初始门店）
- **迁移**：SQLite 文件可迁移至任何平台，无需额外配置
- **日志**：位于 `logs/app.log`，按 10MB 大小轮转，保留 7 份
